# 5.0.1：重复掉线的证据采集

这是诊断更新，不是已确认解决 QQ 登录失效的稳定性修复。聊天模型、账号权限、QQ/NapCat 版本、设备标识与下线处理策略不因该更新而改变。

## 复发事实

2026-11-01 17:44:09（北京时间），QQ 再次通知当前登录失效，距下午重新扫码约两小时。服务器、两个容器均未重启，无 OOM 记录。掉线前 14 分钟没有收发 QQ 消息，也没有新的账号操作或后台好友申请任务。用户确认账号只在手机及这台云端机器人使用。

QQ 为 3.2.34-53644，NapCat 为 4.18.37。QQ 数据目录持续挂载；`machine-info` 的最后修改时间仍为 10 月 17 日。不能根据这些信息推断客户端设备校验一定通过，但目前没有发现启动时反复改写机器信息、模型主动退出账号或消息高频触发下线的证据。

故障发生在接入层的登录会话，而不是模型推理进程。更底层原因仍未确定：原 NapCat 仅打印 `tipsTitle`、`tipsDesc`，没有记录内核回调实际提供的 `appId`、`instanceId`、`sameDevice`、`kickedType`、`securityKickedType`。这些已丢弃字段无法从旧日志还原。

- [相关实验 PR #1768](https://github.com/NapNeko/NapCatQQ/pull/1768) 未合并且反馈不一致；本次没有应用其反检测、环境清洗、随机化或踢线拦截改动。

- [内核事件结构](https://github.com/NapNeko/NapCatQQ/blob/main/packages/napcat-core/types/msg.ts) 定义了上述字段，但没有足以验证所有数值含义的映射。本次保留原始枚举值，不将数字擅自解释成“风控”或“顶号”。

## 改动

`scripts/cloud/napcat_diagnostics.py` 只接受已核对 SHA256 的 NapCat 4.18.37 bundle，添加 `[QQbotDiag/v1]` 结构化日志。记录内核枚举、布尔字段、会话和 Worker 运行时长，不记录原始回调对象、聊天正文、Cookie 或 QQ 号码。原有离线状态更新和事件继续正常执行，不屏蔽下线通知或伪造在线状态。

原始 bundle SHA256：`96934cbd3a4a7ad4d50bfeeaa10adb600fd142cbb4f1be00ce427287fd5926fb`。诊断 bundle SHA256：`00babe43a5de5ce64f917e7ebc085fbae06f6e86fddf243e6e4e885fbd6b7b87`。未知版本或改动过的 bundle 拒绝自动打补丁。

诊断镜像构建使用 `Dockerfile.napcat-diagnostics`，先完整解包基础镜像内的官方 Shell 发行 ZIP，再覆盖诊断主程序；不能只预放一个主程序而跳过原入口的解包步骤。已通过不挂载账号、不连接外网的新容器认证/登录状态 API 启动检查。线上部署另外核对原主机名、MAC 和 QQ 机器信息文件保持一致。完整验证记录见 [验收 JSON](acceptance-v5.0.1.json)。

运维脚本新增只读命令：

```bash
python3 /opt/qqbot/current/scripts/cloud/ops.py diagnose
```

在服务器创建 `/opt/qqbot/run/qq-diagnostics.enabled` 后，每分钟守护检查在首次发现 QQ 掉线时自动留档一次。恢复真实在线后重新准备捕获下一次掉线；探针失败不会被当作新的下线事件。去重状态持久化，不会每分钟重复存档或重启 QQ。

留档位于 `/opt/qqbot/run/incidents/`，目录 0700、JSON 文件 0600，最多保留 12 份。包含状态、机器信息摘要、可解析的下线枚举和有界的 NapCat 日志尾部。原始尾部可能包含敏感消息或登录 URL，不进入 Git，也不打印到状态输出；对外只返回文件名和诊断记录数。

## 验证与边界

新增测试执行实际 JavaScript 下线回调，确认原因字段保留、私有字段排除、原下线事件继续传播，并覆盖未知版本拒绝、补丁幂等、文件权限、快照去重及守护进程不误重启。完整本机回归 171 项通过；实际 bundle 的 Node 语法检查通过。

这些测试验证诊断可靠性，不验证不会再次掉线。需要下一次真实内核事件才能获得过去没有记录的字段；即使字段存在，也可能只是默认值，仍需结合会话时长及对照数据判断。必要的下一步是持续观测和单因素对照，不能把一次重新扫码成功当成问题已经解决。

## 可选隔离对照

已准备 `observe_qq.py` 与 `qqbot-qq-observation.service`，**不自动启用**。需本人同意测试期间暂停聊天，并先完成 QQ 登录，再手动启动服务。

该对照保持 QQ/NapCat 在线，单独停止 Bot 160 分钟，每 20 秒读取管理页登录状态；QQ 若离线立即留档并结束，时间到也结束，然后恢复 Bot。维护标记使用独立租约，防止守护进程中途拉起 Bot；退出清理及 systemd `ExecStopPost` 只恢复该测试持有的维护租约，不清除其他操作者的维护状态。报告私有保存为 `run/qq-isolation.json`。

`QQ_OFFLINE_WITHOUT_BOT` 可以证明 Bot 不是该次离线的必要条件；`QQ_STILL_ONLINE_WITHOUT_BOT` 只是一次观测，不能反向证明 Bot 必然是原因。探针连续失败另记为 `PROBE_UNAVAILABLE`，不当作 QQ 身份失效。
